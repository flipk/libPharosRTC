# NAT Traversal Assessment & Architectural Analysis

This document provides a detailed architectural assessment of the impact of one or more NAT (Network Address Translation) gateways on `libPharosRTC` and its accompanying demo application.

---

## 1. Baseline Architecture & Assumptions

`libPharosRTC` is designed primarily for **direct, air-gapped, tactical RF, satellite, or isolated local IP networks** where both endpoints can directly route IP packets to each other's host interfaces without intermediate address translation:

- **Empty ICE Configuration**: Both the TypeScript client (`src/ts/WebRtcTransport.ts`) and Python backend (`src/python/webrtc_backend.py`) hardcode `iceServers: []`.
- **ICE-Lite Role**: The Python `aiortc` backend operates in ICE-Lite (passive) mode.
- **Host-Only Candidates**: Endpoints gather only local LAN IP candidates (e.g., `192.168.x.x` or `10.x.x.x`). mDNS (`.local`) candidates generated by modern web browsers are explicitly stripped by `sanitize_sdp_offer()` in `webrtc_backend.py`.
- **Out-of-Band Signaling**: Direct WebSocket TCP connection (default port `8765`, or `2500` in `demo/demo_server.py`).

---

## 2. Scenario Assessments

### Scenario 1: Embedded Server behind a NAT; PC directly on the Internet

#### 1. HTTP & WebSocket Signaling (TCP)
- **Requirement**: The NAT gateway in front of the embedded device **must have Port Forwarding (DNAT)** configured for HTTP and WebSocket ports (e.g., forwarding WAN TCP port `2500` or `8765` to the embedded device's private LAN IP).
- **Impact**: Without port forwarding, the PC on the WAN side cannot initiate the TCP connection required to fetch the Web UI or perform SDP signaling.

#### 2. WebRTC Data Channel (UDP)
- **Impact on current codebase**: **Failure**. The server (`aiortc`) generates an SDP Answer containing only its local private LAN IP (e.g., `10.0.0.5:ephemeral_UDP_port`). The PC receives this SDP Answer and tries to send UDP STUN Binding Requests to `10.0.0.5`, which is unroutable across the public Internet.
- **Where STUN/TURN come in**:
  - **STUN / Public IP Advertising**: The embedded server needs STUN (or explicit public IP configuration in `aiortc`) to discover its public WAN IP and port mapping on the NAT gateway so it can advertise its public IP in the SDP Answer.
  - **Port Forwarding**: Alternatively, a static UDP port range must be forwarded on the server's NAT gateway, and `aiortc` must be configured with a public IP override.
  - **TURN**: If the server's NAT gateway does not permit inbound unsolicited UDP traffic or performs restrictive translation, a TURN relay server on the public Internet is required.

---

### Scenario 2: PC behind a NAT; Embedded Server directly on the Internet (Public IP)

#### 1. HTTP & WebSocket Signaling (TCP)
- **Works out-of-the-box**: The PC initiates outbound TCP connections to the embedded server's public IP. Standard stateful NAT gateways track outbound TCP connections automatically, allowing response traffic through without any port forwarding on the PC's NAT.

#### 2. WebRTC Data Channel (UDP)
- **Impact on current codebase**: **Failure**. Because `iceServers: []` is hardcoded in the browser client, the browser gathers only local LAN candidates (e.g., `192.168.1.50`) and `.local` mDNS candidates (which the server strips). The server receives an offer containing only `192.168.1.50` and attempts to send UDP packets to that private IP, which fails.
- **Where STUN comes in**:
  - **Client STUN is REQUIRED**: If the client is supplied with a public STUN server (e.g., `stun:stun.l.google.com:19302`), the browser discovers its **server-reflexive candidate** (`srflx`, e.g., `203.0.113.50:45678`).
  - The browser includes `203.0.113.50:45678` in its SDP offer.
  - When the browser sends its initial outbound STUN Binding Request to the server's public IP/port, it **punches a hole** in the PC's NAT.
  - The server's ICE-Lite stack receives the packet, learns the PC's reflexive WAN IP/port, and replies through the punched hole, completing the DTLS/SCTP handshake.
- **Where TURN comes in**:
  - If the PC is behind a **Symmetric NAT** (common on cellular/mobile CGNAT networks or strict corporate firewalls) or if outbound UDP traffic on non-standard ports is blocked by a firewall, STUN hole punching will fail, and a **TURN relay server** on the public Internet is required.

---

### Scenario 3: Both PC and Embedded Server behind separate NAT Gateways

#### 1. HTTP & WebSocket Signaling (TCP)
- **Impact**: Neither side can initiate a direct TCP connection to the other.
- **Requirement**: Either the embedded server's NAT gateway must have port forwarding configured for the HTTP/WebSocket ports, or signaling must be hosted on an intermediate public web/signaling server that both endpoints connect out to.

#### 2. WebRTC Data Channel (UDP)
- **Impact on current codebase**: **Complete failure**. Both sides exchange unreachable private LAN IP addresses.
- **Where STUN comes in**:
  - Both peers must be configured with STUN servers to obtain server-reflexive (`srflx`) WAN candidates.
  - **P2P NAT Hole Punching**: If **both** NAT gateways are "Cone" NATs (Full Cone, Address-Restricted, or Port-Restricted), simultaneous ICE connectivity checks from both sides can punch bidirectional holes through both NAT gateways, allowing direct peer-to-peer UDP communication.
- **Where TURN comes in**:
  - **MANDATORY if either NAT is Symmetric / CGNAT**: If either endpoint is behind a **Symmetric NAT** (typical for LTE/5G cellular connections, Carrier-Grade NAT / CGNAT, or strict enterprise networks), the NAT assigns a different public UDP port for each remote destination. The port discovered via STUN will not match the port opened for the peer, causing direct NAT hole punching to fail 100% of the time.
  - In this situation, a **TURN relay server** hosted on a publicly accessible server is mandatory. Both peers create allocations on the TURN server over UDP, TCP, or TLS, and all WebRTC datagram traffic is relayed through the TURN server.

## 4. Self-Contained Endpoint-Hosted STUN/TURN Architecture

To maintain `libPharosRTC`'s core design principle of **zero-dependency, air-gapped, zero-install deployment** without relying on third-party cloud STUN/TURN infrastructure (such as Google STUN or Coturn servers), STUN and TURN server capabilities can be hosted directly on whichever endpoint is publicly or directly reachable.

### 1. Scenario 2 (PC behind NAT, Embedded Server directly reachable / Public IP)
- **Embedded STUN Server**:
  - The Python server on the embedded device hosts a lightweight STUN server (e.g., listening on UDP port `3478` or co-located with WebRTC ports).
  - The browser client is dynamically configured during signaling with `iceServers: [{ urls: 'stun:<embedded-device-ip>:3478' }]`.
  - When the browser sends a STUN Binding Request to the embedded device, it **punches a hole** in the PC's NAT gateway.
  - The embedded STUN server responds with the PC's server-reflexive address (`srflx` candidate), which the browser includes in its SDP offer.
  - Direct P2P WebRTC communication succeeds through the punched hole with zero external dependencies.
- **Embedded TURN Server**:
  - If the PC is behind a strict **Symmetric NAT** or CGNAT where STUN hole punching fails, a lightweight TURN relay hosted on the embedded device allows the PC to relay WebRTC datagrams directly over UDP/TCP to the embedded device.

### 2. Scenario 1 (Embedded Server behind NAT, PC directly reachable / Public IP)
- **PC-Hosted STUN Server**:
  - A lightweight STUN server hosted on the PC (or embedded in a desktop launcher/service) allows the embedded device to discover its reflexive WAN IP/port and punch an outbound UDP hole towards the PC.
- **Signaling Consideration**:
  - Because HTTP/WebSocket TCP connection attempts from the PC would be dropped by the server's NAT router without port forwarding, signaling must be flipped so the embedded server initiates an **outbound WebSocket connection** to a signaling receiver on the PC.

### 3. Scenario 3 (Both endpoints behind separate NATs)
- **Direct Limitation**: If neither endpoint is directly reachable or port-forwarded, neither peer can reach a STUN/TURN server hosted on the other (a "chicken-and-egg" problem).
- **Single Port-Forwarding Reduction**: If *at least one* NAT gateway has a static port forwarding (DNAT) rule configured for port 3478/UDP, that endpoint can host the STUN/TURN server for the link, effectively reducing Scenario 3 to Scenario 1 or 2.

### Summary of Endpoint-Hosted Optimization

| Scenario | Self-Contained STUN/TURN Location | Eliminates External Servers? | Operational Notes |
| :--- | :--- | :--- | :--- |
| **Scenario 2** (PC behind NAT, Server reachable) | **Embedded Device** | **Yes** (100% self-contained) | Client `iceServers` points directly to embedded device. Fully solves hole punching. |
| **Scenario 1** (Server behind NAT, PC reachable) | **PC** | **Yes** | Embedded device sends outbound STUN to PC. Signaling must also be initiated outbound by server. |
| **Scenario 3** (Both behind separate NATs) | Neither (unless 1 router has DNAT) | No (Requires external public relay or 1 DNAT rule) | If 1 router has a port forward, that endpoint acts as the STUN/TURN host for the connection. |

## 5. Relevant Code References

If NAT traversal capability is added to `libPharosRTC` in the future, the following code locations define the current host-only behavior:

1. **Client ICE Configuration**: `src/ts/WebRtcTransport.ts`
   ```typescript
   this.pc = new RTCPeerConnection({ iceServers: [] });
   ```
2. **Server ICE Configuration**: `src/python/webrtc_backend.py`
   ```python
   pc = RTCPeerConnection(RTCConfiguration(iceServers=[]))
   ```
3. **mDNS Candidate Filter**: `src/python/webrtc_backend.py` (`sanitize_sdp_offer()`)
   ```python
   # Strips .local mDNS candidate lines from browser SDP offers
   filtered = [l for l in lines if not ("a=candidate:" in l and ".local" in l)]
   ```
